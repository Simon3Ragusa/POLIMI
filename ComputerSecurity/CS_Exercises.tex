\subsection{Exercise 1 - Introduction to Computer Security}
\subsubsection*{Problem}
A national energy provider has rolled out 'SmartMeters' to residential homes... 1. [1.5 points] Identify and describe the 2 most relevant assets at risk... 1.2 [1.5 points] Suggest at least two potential attack surfaces... 1.3 [1 point] A junior engineer proposes a new authentication protocol...

\subsubsection*{Solution}
\begin{itemize}
    \item[\textbf{1.}] Asset 1: Grid Stability / Continuous Power Supply. Threat: A coordinated attack sending 'remote disconnect' commands to thousands of meters simultaneously, causing a blackout or grid instability. Threat Agent: Nation-State Actors / Cyberterrorists. Motivation: To cause social chaos or national infrastructure damage. Geopolitical disruption or warfare. Asset 2: User Privacy (Granular Usage Data). Threat: Profiling user habits (e.g., determining when the house is empty) based on real-time power consumption data. Threat Agent: Criminal Gangs / Burglars. Motivation: To facilitate physical burglary or targeted surveillance. Identifying low-risk targets for physical theft.
    \item[\textbf{1.2}] Attack Surface 1: Physical Optical Port. Motivation: Accessing the physical port on the meter (often located outside the home) allows an attacker to inject commands or read memory directly, bypassing network firewalls. The proprietary, unencrypted protocol makes this easier to reverse-engineer. Attack Surface 2: Cellular Network Interface (LTE). Motivation: The wireless communication channel is exposed to the public. If the TLS implementation is flawed or if the device accepts unsolicited incoming connections, attackers could exploit the network stack remotely.
    \item[\textbf{1.3}] Weakness: Lack of Mutual Authentication. The protocol only authenticates the terminal to the meter. It does not authenticate the meter to the terminal. An attacker could install a fake meter to harvest the terminal's responses or trick the technician. Mitigation: Implement Mutual Authentication where both parties verify each other's identity, ideally using digital certificates (PKI) rather than a simple shared secret hash.

\end{itemize}
\#\#\# Improved Step-by-Step Explanation:
For 1: The 'remote disconnect' feature is highly critical; mass exploitation directly impacts the national power grid, a prime target for nation-state attackers aiming for disruption. The granular power usage data acts as a proxy for physical presence, making it a valuable asset for criminals planning burglaries. Understanding these assets and their associated threats is key to prioritizing security measures.
For 1.2: The optical port represents a local, physical attack surface, compounded by its use of an unencrypted, proprietary protocol that lacks robust security testing. The LTE interface represents a remote attack surface; despite using TLS 1.2, vulnerabilities in the TLS stack or insecure device configuration (e.g., open ports) could be exploited from anywhere on the cellular network.
For 1.3: The proposed protocol is vulnerable to rogue devices. Because the terminal computes a res  ponse based on the meter's challenge without challenging the meter in return, the meter's identity is never verified. A malicious actor could spoof a meter, send challenges, and observe the terminal's valid responses. To fix this, the authentication must be mutual, ensuring that the terminal also challenges the meter and verifies its authenticity before proceeding.

\begin{itemize}

    \item \textbf{Threat}: Spoofing (Biometric Bypass). Attackers can create artificial "gummy" fingers using silicone, gelatine, or 3D-printed materials lifted from latent prints left on the scanner or nearby surfaces.
    \item \textbf{Mitigation}: Implement Multifactor Authentication (e.g., requiring both a fingerprint and an RFID card) or utilize more sophisticated biometric scanners that include liveness detection (checking pulse, blood flow, or heat).
    \item[\textbf{2.}] \textbf{Asset}: Scanned Fingerprint Data (User Biometric Information).
    \item \textbf{Threat}: Data Breach. If the local storage is physically accessed or hacked over a network, attackers could steal raw fingerprint templates, which cannot be changed like passwords.
    \item \textbf{Mitigation}: Fingerprint templates must be stored cryptographically hashed or securely encrypted within a dedicated tamper-proof hardware module (Secure Enclave), ensuring the raw image is never accessible.

\end{itemize}
\textbf{Step 2: Analyzing Numpad Additions}
\begin{itemize}
    \item \textbf{Scenario}: Adding a numpad with an anti-peeping cover.
    \item \textbf{Most Likely Attack}: Given the anti-peeping cover prevents "snooping" (shoulder surfing), the most viable attack becomes \textbf{Guessing/Brute-forcing}. Attackers could observe wear patterns on the keys or methodically try common PINs.
    \item \textbf{Mitigation}: Enforce PIN complexity rules (disallow 1234, 0000), require periodic PIN changes, and implement a lockout mechanism (e.g., locking the pad for 5 minutes after 3 failed attempts) to neutralize brute-force attacks.
\end{itemize}

\subsection{Exercise 1 - Introduction to Computer Security (4 points)}
\subsubsection*{Problem}
Consider a dam equipped with a Supervisory Control And Data Acquisition (SCADA) system, an industrial control system used to monitor and control the dam's operations. The SCADA system collects data from various sensors (e.g., water level, flow rate, temperature) and sends it to a central control room, where operators can monitor the dam's status and make adjustments as needed. The system also controls the opening and closing of gates and valves, as well as the operation of pumps and turbines. The SCADA system is connected to the Internet for remote monitoring and control, and it uses a combination of wired and wireless communication protocols.
[1.5 points] 1. Identify and describe two relevant assets at risk in such a scenario, along with their associated threats and threat agents. All elements must be motivated.
[1 point] 2. Suggest at least two potential attack surfaces for the infrastructure under analysis.
[1.5 points] 3. A friend of yours suggests using a custom challenge and response protocol to authenticate devices for â€œremote monitoring and controlâ€ that works as follows: devices involved in the communication have to share the SHA3 of a preshared secret, securely stored in each device. If the hashes match on both endpoints, the authentication is successful. Highlight the weaknesses of the proposed protocol and suggest a modification to make it working.

\subsubsection*{Solution}
\textbf{Step 1: Identifying Assets, Threats, and Threat Agents.}
An asset is anything of value that needs protection. In a dam's SCADA system, the most obvious asset is the \textbf{Dam Infrastructure} itself, both physical (gates, valves, turbines) and cyber (control systems, servers). A threat is a potential cause of an unwanted incident. For the infrastructure, a major threat is \textbf{unauthorized remote access or manipulation}, which could cause devastating effects like flooding. The threat agent, or the entity causing the threat, could be \textbf{malicious hackers or state-sponsored actors} motivated by sabotage. Another critical asset is the \textbf{Environmental Impact/Safety}. The threat here is the release of large amounts of water causing environmental damage, and the threat agent could be \textbf{eco-terrorists or disgruntled individuals}.

\textbf{Step 2: Identifying Attack Surfaces.}
An attack surface is the sum of all points where an unauthorized user can try to enter data to or extract data from an environment.
\begin{itemize}
    \item \textbf{The SCADA system itself:} Software vulnerabilities in the SCADA software.
    \item \textbf{Communication networks:} Interception of wireless or wired data transmission (e.g., lack of encryption).
    \item \textbf{Physical access:} If an attacker can walk up to a sensor or control panel and tamper with it.
    \item \textbf{Remote access points:} Maintenance ports or remote desktop interfaces for administrators.
    \item \textbf{Human operators:} Social engineering attacks like phishing against the operators.

\end{itemize}
\textbf{Step 3: Analyzing the Authentication Protocol.}
The proposed protocol just sends \texttt{SHA3(secret)} over the network.
\begin{itemize}
    \item \textbf{Lack of Freshness (Replay Attack):} The hash is static. An attacker can sniff \texttt{SHA3(secret)} and simply replay it later to authenticate, without knowing the secret itself.
    \item \textbf{Man-in-the-Middle (MitM):} No session key is established, so an attacker could intercept subsequent commands.
    \item \textbf{No Mutual Authentication:} The device doesn't know if it's talking to the real control room or an imposter server.
    \item \textbf{Preshared Secret Management:} Storing the same secret everywhere is risky; if one device is compromised, all are at risk if the same secret is used.

\end{itemize}
\textbf{How to fix it:}
To prevent replay attacks, we need *freshness*. We can introduce a \textbf{Nonce} (number used once). The control server sends a random nonce $N$, and the device replies with \texttt{HMAC(secret, N)}. This guarantees the response is fresh for this specific session. To ensure the device also trusts the server, we need \textbf{Mutual Authentication}: the device also sends a nonce $M$ to the server, and the server replies with \texttt{HMAC(secret, M)}. Finally, instead of plain hashing, using a standard construct like \textbf{HMAC} prevents length-extension attacks and properly mixes the key and the message.

    \item \textbf{Threat}: A potential cause of an incident that may result in harm to a system or organization.

\begin{itemize}
    \item[\textbf{1.}] \textbf{Asset: Payment Gateway / Credit Card Information}
    \item \textbf{Threat}: Unauthorized access, interception, or exfiltration of sensitive financial data.

    \item[\textbf{2.}] \textbf{Asset: Quality of Service (QoS) and Availability (Infotainment System)}

When prioritizing threats, we consider the likelihood and impact. For an in-flight system, physical access and local network access are highly relevant.
\begin{itemize}
    \item[\textbf{1.}] \textbf{Physical Access Tampering}: The most direct threat. Passengers have prolonged physical access to the hardware components (screens, cables, USB ports). *Threat Agent*: Malicious passengers attempting to tamper with the device directly.
    \item[\textbf{2.}] \textbf{Unauthorized Access via External Interfaces}: Exploiting exposed USB ports, maintenance ports, or hidden diagnostic interfaces. *Threat Agent*: Tech-savvy passengers or hardware hackers.
    \item[\textbf{3.}] \textbf{Wi-Fi Infrastructure Vulnerabilities}: Exploiting weak encryption, rogue access points, or network misconfigurations to intercept traffic. *Threat Agent*: Attackers on board the same flight.

\end{itemize}
\textbf{Question 3: Biometric Authentication for In-Flight Payments}

\begin{itemize}
    \item \textbf{Security}: Biometrics are inherently tied to the individual, making them difficult to forge, guess, or steal remotely compared to passwords.
    \item \textbf{Convenience}: Passengers do not need to remember complex passwords, improving the user experience.

\end{itemize}
*Disadvantages:*
\begin{itemize}
    \item \textbf{Privacy and Data Protection}: Biometric data is sensitive. If compromised, the theft is catastrophic because a fingerprint cannot be changed.
    \item \textbf{Implementation Costs and Maintenance}: Equipping every seat with high-quality, reliable biometric sensors is expensive.
    \item \textbf{Spoofing Vulnerabilities}: Without sophisticated liveness detection, biometric systems can sometimes be bypassed using fake fingerprints or high-resolution photos.

\end{itemize}
*Conclusion:* While convenient, storing or processing biometric data on vulnerable seatback screens introduces severe privacy risks. Robust security measures must be implemented to protect the data and prevent spoofing.

\subsubsection*{Problem}
The widespread use of drone technology has revolutionized various industries, including aerial photography, delivery services, and infrastructure inspections. However, the increasing accessibility and capabilities of drones also raise concerns about their potential misuse for malicious purposes. Consider a scenario where a company utilizes drones for aerial surveillance and package delivery:
\begin{itemize}
    \item The company operates a fleet of drones equipped with high-resolution cameras and GPS navigation systems.
    \item The drones transmit real-time video feeds and telemetry data over a 5G network back to the central control station. The communication protocol uses an MD5 checksum for data integrity.
    \item The collected surveillance footage and delivery data are stored on the company's servers, with access protected by MD5 salted and hashed passwords. The server operating system is Windows 2000 Server.
    \item The company website, where customers can track their deliveries, is served over HTTP.

\end{itemize}
Answer the following questions, considering the security implications of drone usage in this specific scenario only:
[1.5 points] 1. Identify and describe the 2 most relevant assets at risk in such a scenario, along with their associated threats and threat agents. All elements must be motivated.
[1.5 points] 2. Identify 2 potential vulnerabilities in the company's drone operations, specifying how it can be exploited by threat agents and a possible countermeasure.
[1 point] 3. As a password recovery scheme, the company decides to implement the following mechanism: when a user asks to reset their password, an email is sent to the user with a new randomly generated password. This password is created by combining a randomly selected word (up to 9 lower case characters) from a dictionary of animal names with a randomly generated 3-digit number (e.g., "dolphin451"). Analyze the security of this password recovery scheme. Identify its potential weaknesses and suggest improvements to enhance its security.

\subsubsection*{Solution}
\#\#\# 1. Identifying Assets, Threats, and Threat Agents
\textbf{Step-by-Step Reasoning:}
When identifying assets, we look for data, hardware, or systems critical to the operation or containing sensitive information.
\begin{itemize}
    \item \textbf{Asset 1: Surveillance Footage and Delivery Data}
    \item *Motivation:* This data is highly sensitive, revealing customer routines, private premises, and company operations.
    \item *Threat:* Unauthorized access, data breaches, and data exfiltration (violating Confidentiality).
    \item *Threat Agent:* Hackers motivated by financial gain (selling data), competitors, or malicious actors aiming for blackmail.
    \item \textbf{Asset 2: Drones (Physical and Operational Assets)}
    \item *Motivation:* Drones are expensive physical hardware and are the core operational mechanism for the company.
    \item *Threat:* Hijacking, interception, physical theft, or signal jamming (violating Availability and Integrity).
    \item *Threat Agent:* Criminals aiming to steal the hardware, competitors seeking to disrupt operations, or malicious actors wanting to repurpose the drones.

\end{itemize}
\#\#\# 2. Vulnerabilities, Exploits, and Countermeasures
\textbf{Step-by-Step Reasoning:}
We analyze the scenario description for outdated technologies or insecure practices.
\begin{itemize}
    \item \textbf{Vulnerability 1: Outdated Server Operating System (Windows 2000 Server)}
    \item *Exploitation:* Windows 2000 has been unsupported for decades. It lacks modern security patches. Attackers can exploit well-known, unpatched CVEs (e.g., buffer overflows, RPC vulnerabilities) to achieve Remote Code Execution (RCE) and take full control of the servers.
    \item *Countermeasure:* Upgrade to a modern, actively supported Operating System (e.g., Windows Server 2022 or a supported Linux distribution) and implement a regular patch management policy.
    \item \textbf{Vulnerability 2: Use of HTTP for the Company Website / MD5 for Hashing}
    \item *Exploitation (HTTP):* HTTP traffic is unencrypted plaintext. Attackers can perform Man-in-the-Middle (MitM) attacks on the network to eavesdrop on customer data or hijack sessions.
    \item *Exploitation (MD5):* MD5 is cryptographically broken and vulnerable to collision attacks. It can be easily cracked using rainbow tables or brute-force using modern GPUs.
    \item *Countermeasure:* Enforce HTTPS (TLS 1.2/1.3) to encrypt data in transit. Replace MD5 with a strong, slow hashing algorithm like Argon2, bcrypt, or at least SHA-256 with proper salting.

\end{itemize}
\#\#\# 3. Password Recovery Scheme Analysis
\textbf{Step-by-Step Reasoning:}
To evaluate the password strength, we calculate the entropy (the number of possible combinations).
\begin{itemize}
    \item \textbf{Dictionary size:} Animal names (assumed to be a relatively small dictionary, e.g., a few thousand words). Let's say 1,000 words.
    \item \textbf{Numbers:} 3 digits = 1,000 combinations (000-999).
    \item \textbf{Total combinations:} 1,000 words * 1,000 numbers = 1,000,000 possible passwords.
    \item \textbf{Vulnerability:} 1 million combinations can be cracked in less than a second by a modern GPU. The structure is predictable (word + number), there are no special characters, and lowercase only limits the character space.
    \item \textbf{Delivery Risk:} Sending plaintext passwords via email is highly insecure. Emails traverse networks unencrypted (if TLS is misconfigured) and reside in the user's inbox in plaintext, easily compromised.
    \item \textbf{Improvements:}
    \item[\textbf{1.}] Do not generate and send plaintext passwords. Instead, generate a secure, single-use, time-limited reset link containing a cryptographically secure token.
    \item[\textbf{2.}] Implement Multi-Factor Authentication (MFA).
    \item[\textbf{3.}] Require users to choose their own strong password upon clicking the link, enforcing length (e.g., minimum 12-16 characters) and complexity policies, rather than relying on a weak dictionary generation.
\end{itemize}

[3 points] 2. \subsubsection*{Solution}
\textbf{Step 1: Analyzing the CTR mode nonce selection.}
AES in Counter (CTR) mode turns a block cipher into a stream cipher. It encrypts a sequence of counters to produce a keystream, which is then XORed with the plaintext: $C = P \oplus E_k(Counter)$.
A fundamental rule of stream ciphers (and CTR mode) is that the *same keystream must never be reused*. If the key is the same (derived from the user's password) and the initial counter (nonce) is the same, the keystream will be identical.
In this scheme, the initial counter is the \textbf{first 16 characters of the filename}. This is extremely dangerous. If two files have the same first 16 characters (e.g., \texttt{financial\_report\_2022.pdf} and \texttt{financial\_report\_2023.pdf}), they will share the exact same initial counter and thus the same keystream.
\textbf{The Leakage:} If $C_1 = P_1 \oplus KS$ and $C_2 = P_2 \oplus KS$, an attacker can compute $C_1 \oplus C_2 = (P_1 \oplus KS) \oplus (P_2 \oplus KS) = P_1 \oplus P_2$. This completely exposes the XOR difference between the two plaintexts, breaking confidentiality.
\textbf{The Fix:} The nonce (initial counter value) must be unique for *every* encryption operation. A simple fix is to generate a random 128-bit (16-byte) value using a Cryptographically Secure Pseudo-Random Number Generator (CSPRNG) for each file, and store this nonce alongside the encrypted file.

\textbf{Step 2: Calculating Diceware Entropy.}
A uniformly random AES-256 key has 256 bits of entropy.
We want to achieve the same entropy using a Diceware passphrase. In Diceware, we select words randomly from a dictionary.
The dictionary size is $2^{16}$.
The entropy of choosing one word uniformly at random from this dictionary is $\log_2(2^{16}) = 16$ bits.
Since each word choice is independent, the total entropy of a sequence of $N$ words is $N \times 16$ bits.
We need $N \times 16 = 256 \implies N = 256 / 16 = 16$.
Therefore, a user would need to randomly select and string together \textbf{16 words} from the dictionary to achieve the equivalent security of a 256-bit random key.

\textbf{Question 1: Impersonating User A}
*Understanding the Protocol:*
\begin{itemize}
    \item[\textbf{1.}] User A generates a 1000-bit random string $R$ and appends 24 zeros: $M = R || 0^{24}$.
    \item[\textbf{2.}] A "signs" $M$ using their private decryption key: $S = Dec(K_{privA}, M)$.
    \item[\textbf{3.}] A encrypts $S$ for B: $C = Enc(K_{pubB}, S)$ and sends it.
    \item[\textbf{4.}] B decrypts $C$: $S' = Dec(K_{privB}, C)$.
    \item[\textbf{5.}] B verifies A's "signature": $M' = Enc(K_{pubA}, S')$. If the last 24 bits are zeros, B accepts the session key.

\end{itemize}
*Finding the Flaw (Existential Forgery):*
The vulnerability lies in how the "signature" is verified. B only checks if the resulting plaintext ends in 24 zeros. Since the attacker E knows A's public key, E can work backwards using a guess-and-check approach:
\begin{itemize}
    \item[\textbf{1.}] E guesses a random 1024-bit string $S_{guess}$.
    \item[\textbf{2.}] E computes $M_{guess} = Enc(K_{pubA}, S_{guess})$.
    \item[\textbf{3.}] E checks if the last 24 bits of $M_{guess}$ are all zeros.
    \item[\textbf{4.}] If not, E tries a new $S_{guess}$.

\end{itemize}
The probability of finding a match is $1 / 2^{24}$ (approx. 16.7 million attempts). This takes only a few minutes on a modern computer. Once found, E encrypts $S_{guess}$ with B's public key and sends it. B will verify it successfully with A's public key, allowing E to successfully impersonate A.

\textbf{Question 2: Replacing Encryption with Proper Signatures}
*Analyzing the Change:*
The protocol proposes replacing decryption with a proper digital signature algorithm ($Sign$) and encryption with verification ($Verify$).

A signature verification algorithm ($Verify(Key, Message, Signature)$) does not output a recoverable plaintext message; it outputs a boolean value (True or False) indicating whether the signature is valid.
If the protocol requires User A to perform a "signature verification action" on a random string (as a replacement for the second encryption step), it is impossible because A does not have a signature generated by B to verify against. Therefore, the choice is not viable because the protocol would break mechanically and fail to execute.

\#\#\# 1. Cryptographic Protocol Design for File Storage
\textbf{Step-by-Step Reasoning:}
The service does not authenticate users, and we cannot trust it with confidentiality or integrity. Thus, all security must be implemented client-side (Zero-Knowledge architecture).
\begin{itemize}
    \item \textbf{Confidentiality:} The client must encrypt files before uploading them so the server cannot read them. A symmetric algorithm like AES-256 is ideal.
    \item \textbf{Integrity \& Authenticity:} The client must ensure the server hasn't tampered with the ciphertext. A Message Authentication Code (MAC), such as HMAC or AES-CMAC, should be computed over the ciphertext. Authenticated Encryption (like AES-GCM) covers both.
    \item \textbf{Deleting files securely:} Since the server can't be trusted to verify identity, anyone could theoretically ask to delete a file. We need an authorization mechanism. The client can attach a secret \texttt{DELETETOKEN} to the file upon creation. To delete, the client proves knowledge of this token.

\end{itemize}
\textbf{Proposed Protocol:}
\begin{itemize}
    \item[\textbf{1.}] \textbf{Setup:} The client generates local symmetric keys and maintains a local index mapping file names to keys.
    \item[\textbf{2.}] \textbf{Create:} The client generates a random \texttt{DELETETOKEN}. The file content is encrypted with a symmetric key (e.g., AES-256-CTR). The client computes a MAC over the ciphertext + the \texttt{DELETETOKEN}. The ciphertext and MAC are uploaded.
    \item[\textbf{3.}] \textbf{Read:} The client downloads the file, verifies the MAC using the local symmetric key, and decrypts the content if the verification passes. This prevents reading modified data.
    \item[\textbf{4.}] \textbf{Update:} The client essentially performs a Delete of the old file and a Create of the new file.
    \item[\textbf{5.}] \textbf{Delete:} The client sends a deletion request containing the \texttt{DELETETOKEN} and the MAC computed over (file ID + \texttt{DELETETOKEN}). The server verifies the MAC and deletes the file only if it matches. This prevents unauthorized users from deleting files.

\end{itemize}
\#\#\# 2. Password Brute-Force Strategies Analysis
\textbf{Step-by-Step Reasoning:}
First, we calculate the total password space (combinations).
Diceware uses 3 words from a 2000-word dictionary.
Total combinations = 2000\textasciicircum{}3 = 8 * 10\textasciicircum{}9 (8 billion).
The probability of a single guess being correct is 1 / (8 * 10\textasciicircum{}9) = 1.25 * 10\textasciicircum{}-10.

\textbf{Strategy 1: 10 Attempts Lockout}
\begin{itemize}
    \item We want the probability of cracking to be < 10\textasciicircum{}-9 (1 in a billion).
    \item The attacker gets 10 attempts.
    \item Probability of success in 10 attempts = 10 * (1.25 * 10\textasciicircum{}-10) = 1.25 * 10\textasciicircum{}-9.
    \item \textbf{Conclusion:} 1.25 * 10\textasciicircum{}-9 is greater than the strict limit of 1.0 * 10\textasciicircum{}-9. Therefore, Strategy 1 \textbf{does not} meet the requirement.

\end{itemize}
\textbf{Strategy 2: Incremental Delay (10ms increase per attempt)}
\begin{itemize}
    \item We want cracking to take > 120 years on average.
    \item On average, the attacker needs to try half the password space to succeed: (8 * 10\textasciicircum{}9) / 2 = 4 * 10\textasciicircum{}9 attempts.
    \item The delay increases arithmetically: 10ms, 20ms, 30ms ... 10 * N ms.
    \item Total time T for N attempts is the sum of an arithmetic progression: T = N * (N * 10) / 2 ms.
    \item Average time = (4 * 10\textasciicircum{}9) * (4 * 10\textasciicircum{}9 * 10) / 2 ms
\end{itemize}
= 16 * 10\textasciicircum{}19 / 2 ms = 8 * 10\textasciicircum{}19 ms.
\begin{itemize}
    \item Convert to seconds: 8 * 10\textasciicircum{}16 seconds.
    \item Convert to years: 8 * 10\textasciicircum{}16 / (3600 * 24 * 365) = 2.5 * 10\textasciicircum{}9 years (2.5 billion years).
    \item \textbf{Conclusion:} 2.5 billion years is massively larger than 120 years. Therefore, Strategy 2 \textbf{perfectly meets} the requirement and works in practice.
\end{itemize}

\subsubsection*{Problem}
You have intercepted two ciphertexts:
c1 = 1111100101111001110011000001011110000110
c2 = 1111101001100111110111010000100110001000

You know that both are OTP ciphertexts, encrypted with the same key.

\begin{itemize}
    \item[\textbf{1.}] [2 points] You know that either c1 is an encryption of alpha and c2 is encryption of bravo or c1 is an encryption of delta and c2 is an encryption of gamma (all converted to binary from ascii in the standard way). Which of these two possibilities is correct, and why?
    \item[\textbf{2.}] [1 point] What was the key k? Explain a procedure to obtain the key
    \item[\textbf{3.}] [2 points] Suppose now that the encryption algorithm is modified as follows:
\end{itemize}
EAVESDROP'($m \in \{0, 1\}^\lambda$):
$k \gets \{0, 1\}^\lambda$
c := k XOR m
return (k, c)
Please, explain the weakness of the proposed approach.

\subsubsection*{Solution}
\textbf{1.} Since c1 and c2 are encrypted with the same One-Time Pad (OTP) key, XORing the two ciphertexts together will cancel out the key: \texttt{c1 XOR c2 = (m1 XOR k) XOR (m2 XOR k) = m1 XOR m2}.
First, compute \texttt{c1 XOR c2}:
c1 = 11111001 01111001 11001100 00010111 10000110
c2 = 11111010 01100111 11011101 00001001 10001000
c1 XOR c2 = 00000011 00011110 00010001 00011110 00001110

Next, compute the XOR of the ASCII binary values for the first possibility ("alpha" and "bravo"):
'a' XOR 'b' = 01100001 XOR 01100010 = 00000011
'l' XOR 'r' = 01101100 XOR 01110010 = 00011110
'p' XOR 'a' = 01110000 XOR 01100001 = 00010001
'h' XOR 'v' = 01101000 XOR 01110110 = 00011110
'a' XOR 'o' = 01100001 XOR 01101111 = 00001110
This exactly matches \texttt{c1 XOR c2}. Therefore, the correct possibility is that c1 is the encryption of "alpha" and c2 is the encryption of "bravo".

\textbf{2.} To obtain the key \texttt{k}, we simply XOR the ciphertext with its corresponding known plaintext. Due to the properties of XOR, \texttt{c1 = m1 XOR k} implies \texttt{k = c1 XOR m1}.
Using c1 and m1 ("alpha"):
c1 = 11111001 01111001 11001100 00010111 10000110
'a','l','p','h','a' = 01100001 01101100 01110000 01101000 01100001
k  = 10011000 00010101 10111100 01111111 11100111
This provides the secret key.

\textbf{3.} The proposed encryption algorithm EAVESDROP' generates a random key \texttt{k}, computes the ciphertext \texttt{c = k XOR m}, but critically, it returns the pair \texttt{(k, c)}. The weakness is fundamental: by returning the key alongside the ciphertext, anyone who intercepts the message immediately possesses the key required to decrypt it. The attacker simply needs to compute \texttt{m = c XOR k}. This approach completely defeats the purpose of encryption, offering zero confidentiality.

\subsection{Exercise 2 - Introduction to Cryptography}
\subsubsection*{Problem}
Consider the case of a public software archive: the software distributor has designed the following highly efficient scheme to protect the integrity of the distributed software... given a piece of software (e.g. a Linux distribution package), consider it as a (long) bitstring s and distribute the bitstring obtained concatenating the strings a,s,b,c, where: a is obtained as SHA-256(s)... Argue on the fact that the proposed scheme provides integrity and origin authentication... Design a simple and effective scheme to protect the integrity and authenticity...

\subsubsection*{Solution}
\textbf{Step 1: Analyzing the Proposed Scheme}
The scheme claims to provide integrity and origin authentication without key management by simply appending hashes: \texttt{a = SHA-256(s)}, \texttt{b = SHA-256(s||a)}, \texttt{c = SHA-256(a||s||b)}.
\begin{itemize}
    \item \textbf{Integrity Attack}: An attacker can intercept the software \texttt{s}, modify it to malicious \texttt{s'}, and independently recompute the hashes \texttt{a'}, \texttt{b'}, and \texttt{c'} using the same publicly known SHA-256 algorithm. The receiver will hash the modified software and the hashes will perfectly match, meaning the scheme fails to protect integrity.
    \item \textbf{Origin Authentication Attack}: Because there are no secrets (keys) involved in the hash computations, anyone can act as the 'distributor'. An attacker can create entirely new software, compute the required hashes, and claim it originated from the official distributor. There is no proof of origin.

\end{itemize}
\textbf{Step 2: Designing a Secure Scheme}
To securely achieve both properties, we must introduce asymmetric cryptography (Public Key Infrastructure):
\begin{itemize}
    \item[\textbf{1.}] \textbf{Setup}: The distributor generates a public-private key pair. The private key is kept securely by the distributor, and the public key is distributed to users via a trusted channel (e.g., embedded within the OS installation bundle).
    \item[\textbf{2.}] \textbf{Signing (Origin + Integrity)}: The distributor computes a cryptographic hash of the software (e.g., SHA-256) and then encrypts (signs) this hash using their private key.
    \item[\textbf{3.}] \textbf{Verification}: The user downloads the software and the digital signature. The user independently hashes the downloaded software and also decrypts the signature using the distributor's trusted public key. If the two hash values match, it guarantees that the software was signed by the owner of the private key (origin authenticity) and has not been altered since it was signed (integrity).
\end{itemize}

\subsubsection*{Solution}
\textbf{Step 1: Identifying the Vulnerabilities.}
Looking at the \texttt{hackÃ©mon} struct, we see \texttt{name} is a 4-byte buffer.
On line 23, \texttt{scanf("\%112s", h.name);} reads up to 112 bytes into \texttt{name}. This clearly overflows the 4-byte buffer, corrupting adjacent stack memory (\texttt{description}, \texttt{hack\_index}, saved EBP, and saved EIP). This is a \textbf{Buffer Overflow}. To fix it, change the format specifier to bound the input: \texttt{scanf("\%3s", h.name);} (leaving 1 byte for the null terminator).
On line 26, \texttt{printf(h.description);} prints the \texttt{description} string without a format specifier (like \texttt{"\%s"}). If a user can control \texttt{h.description}, they can inject format string specifiers (like \texttt{\%x}, \texttt{\%n}). This is a \textbf{Format String Vulnerability}. To fix it, use \texttt{printf("\%s", h.description);}.

\textbf{Step 2: Exploiting the Buffer Overflow.}
Our goal is to execute a 60-byte shellcode.
The stack layout grows from high to low addresses. Local variables are placed on the stack.
Layout (from lowest to highest address): \texttt{h.name} (4 bytes) -> \texttt{h.description} (36 bytes) -> \texttt{h.hack\_index} (4 bytes) -> \texttt{saved EBP} (4 bytes) -> \texttt{saved EIP} (4 bytes) -> \texttt{Caller's frame}.
Notice that \texttt{h.name} is at the lowest address. When \texttt{scanf} writes to \texttt{h.name}, it writes towards higher addresses, naturally overflowing into \texttt{description}, then \texttt{hack\_index}, \texttt{sEBP}, and finally \texttt{sEIP}.
To redirect execution, we must overwrite the \texttt{sEIP} with the address of our shellcode.
However, we have a problem: the \texttt{while} loop continues as long as \texttt{h.hack\_index > 0}. Because \texttt{h.name} is before \texttt{h.hack\_index} in memory, our overflow will necessarily overwrite \texttt{h.hack\_index} before it reaches \texttt{sEIP}. If we overwrite it with a positive value, the loop will continue, and the function will not return (thus not popping \texttt{sEIP} into \texttt{EIP}). If we overwrite it with $0$ or a negative value, the loop terminates!
Moreover, our shellcode is 60 bytes long. The space between \texttt{h.name} and \texttt{sEIP} is $4 + 36 + 4 + 4 = 48$ bytes. We cannot fit the 60-byte shellcode *before* \texttt{sEIP}. We must place it *after* \texttt{sEIP} (in the caller's stack frame).
\textbf{Exploit Construction:}
\begin{itemize}
    \item[\textbf{1.}] Send 40 bytes of padding (to fill \texttt{name} and \texttt{description}).
    \item[\textbf{2.}] The next 4 bytes will overwrite \texttt{h.hack\_index}. We set these to \texttt{0xFFFFFFFF} (a negative integer in two's complement) so the loop exits immediately.
    \item[\textbf{3.}] Send 4 bytes to overwrite \texttt{sEBP} (can be garbage).
    \item[\textbf{4.}] Send 4 bytes to overwrite \texttt{sEIP}. This must be the memory address pointing exactly to the byte right after this \texttt{sEIP} on the stack.
    \item[\textbf{5.}] Send the 60-byte shellcode.
\end{itemize}
When \texttt{add\_hackÃ©mon} returns, it pops our injected address into \texttt{EIP}, and execution flows directly into our shellcode.

\textbf{Step 3: Bypassing the Stack Canary.}
A Stack Canary places a random, unpredictable value between the local variables and the \texttt{sEBP}/\texttt{sEIP}. Before the function returns, it checks if the canary was modified. Our previous linear overflow would blindly overwrite the canary, failing the check and terminating the program before our shellcode runs.
So, the canary *is* effective against the simple linear BOF.
However, we also have a Format String Vulnerability! We can use it in combination with the BOF to bypass the canary.
If we overflow \texttt{h.name}, we can overwrite \texttt{h.description} *during the scanf call*! \texttt{scanf} happens *after* \texttt{strcpy}. So our overflow from \texttt{h.name} goes into \texttt{h.description}.
Thus, we *can* inject a format string that will be executed by \texttt{printf} on line 26!
To bypass the canary:
\begin{itemize}
    \item[\textbf{1.}] First iteration: Overflow \texttt{h.name} to place a format string payload into \texttt{h.description} that *reads* (leaks) the canary value off the stack using \texttt{\%x} or \texttt{\%p}. Overwrite \texttt{h.hack\_index} with a large number to stay in the loop. Be careful not to overflow all the way to the canary yet.
    \item[\textbf{2.}] Read the leaked canary from the program output.
    \item[\textbf{3.}] Second iteration: Now construct the full BOF payload. We overwrite \texttt{h.name}, \texttt{h.description}, \texttt{h.hack\_index} (with a negative value to exit), write the *correct leaked canary* back into its place, overwrite \texttt{sEBP}, overwrite \texttt{sEIP} with the shellcode address, and append the shellcode. The canary check will pass!

\end{itemize}
\textbf{Step 4: Bypassing Canary + NX.}
NX (No-eXecute) means the stack is not executable. Our shellcode placed on the stack will crash when the CPU tries to run it.
To bypass NX, we cannot execute our injected code. Instead, we must reuse existing executable code in the program's memory or linked libraries (like \texttt{libc}). This is called \textbf{Return-Oriented Programming (ROP)} or \textbf{ret2libc}.
We use the exact same leak-and-overwrite technique as above to bypass the canary. However, instead of overwriting \texttt{sEIP} with a pointer to our shellcode, we overwrite \texttt{sEIP} with the address of the \texttt{system()} function in libc. We then place a fake return address (often \texttt{exit()}) and a pointer to the string \texttt{"/bin/sh"} (which we can also find in libc or place on the stack ourselves). When the function returns, it "returns" into \texttt{system("/bin/sh")}, spawning a shell without executing any stack memory.

\#\#\# Question 1: Obfuscating a Static IP Address

To evade static signature-based detection, the IP address string must not appear in plaintext within the compiled binary.

\textbf{Pedagogical Approaches to Data Obfuscation:}

\begin{itemize}
    \item[\textbf{1.}] \textbf{Simple Encryption (e.g., XOR encoding):}
    \item *Concept:* XOR the IP address string with a hardcoded secret key before compiling. The binary only contains the ciphertext and the key. During execution, the malware XORs the ciphertext with the key again to recover the plaintext IP address in memory.
    \item *Example:* If IP is \texttt{9.7.6.5} and Key is \texttt{0xAA}. The binary stores \texttt{ciphertext = "9.7.6.5" \textasciicircum{} 0xAA}. At runtime: \texttt{IP = ciphertext \textasciicircum{} 0xAA}.
    \item[\textbf{2.}] \textbf{Algorithmic Computation:}
    \item *Concept:* Do not store the IP address at all. Instead, store mathematical operations that, when calculated at runtime, yield the numerical representation of the IP address.
    \item *Example:* To hide \texttt{7.15.6.8}, the code might execute: \texttt{IP = construct\_ip(2+5, 10+5, 3*2, 16/2)}.
    \item[\textbf{3.}] \textbf{Encoding Techniques:}
    \item *Concept:* Represent the IP address using a non-standard encoding scheme (like Base64, Hexadecimal, or a custom alphabet). The AV scanner looking for standard dotted-decimal notation (\texttt{X.X.X.X}) will miss it. The malware decodes it in memory just before initiating the network connection.
    \item *Example:* Storing the hex representation of the 32-bit integer form of the IP, and converting it back to a socket structure at runtime.

\end{itemize}
\#\#\# Question 2: Shortcomings of Using a Known Packer (UPX)

While packing compresses and obfuscates the original code, relying on a common tool like UPX has significant drawbacks against modern Antivirus (AV) solutions.

\textbf{Two Ways AVs Detect Packed Malware:}

\begin{itemize}
    \item[\textbf{1.}] \textbf{Automated Unpacking (Static Reversal):} UPX is a standard, open-source tool. AV engines perfectly understand its compression algorithms and stub structure. When an AV scans a UPX-packed file, it simply runs an internal UPX unpacker to extract the original payload in memory and then scans the extracted, plaintext malware against its signature database.
    \item[\textbf{2.}] \textbf{Heuristic/Dynamic Detection (Suspicion of Packing):} The mere presence of a packing stub (the small bit of code that decompresses the rest) is a strong heuristic indicator of suspicious intent. Legitimate software rarely uses packers like UPX anymore. An AV might flag the file as \texttt{Suspicious.Packed.UPX} purely because it is obfuscated, regardless of the payload's nature. Alternatively, the AV might execute the file in a secure sandbox (dynamic analysis), observe the decompression routine running in memory, and then scan the memory pages once the real payload is exposed.

\end{itemize}
\#\#\# Question 3: Polymorphic vs. Metamorphic Engines

\textbf{Goal:} Hide a known IP address and invariant code fragments generated by a malware builder.

\textbf{Analysis of Options:}

\begin{itemize}
    \item \textbf{Polymorphic Engine:} This engine encrypts the entire main payload (including data sections where the IP might reside and code sections with the generator's signatures) and attaches a unique, varying decryption routine (the stub) to it.
    \item *Pros:* Because the payload is encrypted, the hardcoded IP address and the static signatures of the generator are completely hidden on disk.
    \item *Cons:* Once the malware runs and the stub decrypts the payload into memory, the original payload (with its known signatures and IP) is exposed. If the AV performs memory scanning during execution, it will catch it.

    \item \textbf{Metamorphic Engine:} This engine mutates the *code* itself (instruction substitution, register swapping, inserting junk code) without encrypting it.
    \item *Pros:* The code looks completely different structurally every time, making traditional static signature matching of the *code* impossible.
    \item *Cons:* Standard metamorphic engines primarily focus on altering executable instructions (the \texttt{.text} section), not data. If the IP address is stored as a string constant in a data section (like \texttt{.rdata} or \texttt{.data}), the metamorphic engine will likely leave it untouched.

\end{itemize}
\textbf{Conclusion \& Motivation:}

I would choose the \textbf{Polymorphic Engine}, subject to specific assumptions.

\textbf{Why Polymorphic?} It provides a blanket guarantee that *everything* inside the payloadâ€”both the static code signatures from the generator and the hardcoded IP address in the data sectionâ€”will be encrypted and thus hidden from static disk-based AV scanners.

\textbf{Assumption Required for Polymorphic:} We must assume that the AV relies primarily on *static analysis* of the file on disk. If the AV uses aggressive dynamic behavioral analysis or memory scanning, the decrypted payload will eventually be caught.

*(Alternatively, one could argue for Metamorphic, but with a strict assumption)*

\textbf{Why Metamorphic?} If we assume the AV only scans for code signatures and we are more worried about the AV identifying the decryption stub of a polymorphic engine.

\textbf{Assumption Required for Metamorphic:} We \textbf{must} assume that this specific metamorphic engine is advanced enough to also obfuscate data constants (like strings representing IP addresses) and not just CPU instructions. If it only mutates code, the static IP address string will remain in plaintext, and the static AV will detect it immediately, defeating the purpose.

\begin{itemize}

\begin{itemize}
    \item Since static analysis fails, defenders must use \textbf{Dynamic/Heuristic Analysis}.
    \item \textbf{Execution}: The malware is executed inside a heavily monitored, hardened Virtual Machine (Sandbox).
    \item \textbf{Monitoring}: Security software hooks into the operating system's API to monitor the program's *behavior* rather than its code. If the program attempts to inject code into \texttt{explorer.exe}, modify the registry for persistence, or open a network connection to a known Command \& Control server, the heuristic engine flags it as malicious based purely on its actions.
\end{itemize}

Because dynamic analysis monitors execution behavior in memory *after* decryption, the forged C\&C network response will still trigger the payload, and the sandbox will successfully log the malware's true actions.
\end{itemize}

\end{itemize}

\subsubsection*{Solution}
\begin{enumerate}
    \item[\textbf{5.1}] \textbf{Firewall rules:}
    \begin{itemize}
        \item \texttt{FW1 ANY ANY Int -> DMZ WS\_IP 80 ALLOW} Public to webserver;
        \item \texttt{FW1 L\_DNS\_IP ANY DMZ -> Internet Auth. DNS 53 ALLOW} Local DNS server to auth. one;
        \item \texttt{FW1 ANY ANY ANY ANY ANY DENY} Default deny;
        \item \texttt{FW2 WS\_IP ANY DMZ->BE\_LAN AS\_IP 80 ALLOW} WebServer reaching backend;
        \item \texttt{FW2 ANY ANY DN\_LAN->DMZ L\_DNS\_IP 53 ALLOW} D\&N to local DNS;
        \item \texttt{FW2 AS\_IP ANY BE\_LAN->DMZ L\_DNS\_IP 53 ALLOW} AS reaching DNS;
        \item \texttt{FW2 ANY ANY DN\_LAN AS\_IP 80 ALLOW} D\&N reaching AS;
        \item \texttt{FW2 ANY ANY ANY ANY ANY DENY} Default deny.
    \end{itemize}

    \item[\textbf{5.2}] \textbf{ARP cache poisoning.} \\
    \textbf{Assumptions:} MAC addresses are not cached, Same LAN, ARP is not authenticated: first come, first trust. \\
    \textbf{Attack Description:} The Janitor wants to sniff the full conversation between JD and Turk, thus he needs to become a full-duplex man in the middle. Thus he needs to perform the very same attack twice, once against JD and the other against Turk. 
    \begin{enumerate}
        \item On the first connection, JD sends a broadcast ARP request for Turk's MAC address. 
        \item The Janitor ``wins the race'' against Turk, replying with his own MAC address with a forged ARP reply. 
        \item JD trusts the first ARP reply $\rightarrow$ The Janitor is half-duplex MITM. 
    \end{enumerate}
    The very same attack is then performed against Turk. At the end the Janitor is full-duplex MITM. All the packets he intercepts are forwarded on to preserve the ongoing conversation.

    \item[\textbf{5.3}] \textbf{ATTACK DOABILITY:} The attack is still perfectly doable since it operates at the link layer of the stack, specifically abusing MAC addresses. Since they are still not cached and the Janitor still controls one doctor's workstation he can still put the attack in place. \\
    \textbf{ATTACK EFFECTIVENESS:} The attack is not effective anymore, since HTTPS encrypts the conversation. Thus, the Janitor can become a MITM (even full-duplex) but then he is not able to read the payload of the sniffed traffic.
\end{enumerate}

\subsubsection*{Improved Step-by-Step Explanation:}
\begin{itemize}
    \item \textbf{For 5.1:} The firewall rules enforce the principle of least privilege. The WebServer (WS) in the DMZ must be accessible from the Internet on port 80. The Local DNS server in the DMZ needs to query Authoritative DNS servers on the Internet on port 53. Internal hosts (DN\_LAN and BE\_LAN) need to reach the Local DNS server in the DMZ. The WS needs to communicate with the Application Server (AS) in the BE\_LAN. Doctors and Nurses (DN\_LAN) need to reach the AS. All other traffic is denied by default.
    \item \textbf{For 5.2:} The attack is ARP cache poisoning (ARP spoofing). Because ARP is stateless and unauthenticated, a device will accept an ARP reply even if it didn't send a request, and will generally overwrite existing cache entries. By sending spoofed ARP replies to both JD and Turk, claiming to have the IP address of the other party, the Janitor positions himself as a Man-in-the-Middle, intercepting and forwarding all traffic between them.
    \item \textbf{For 5.3:} The transition to HTTPS does not prevent ARP spoofing because ARP operates at Layer 2 (Data Link Layer), while HTTPS operates at Layer 7 (Application Layer) over TCP/IP (Layers 4/3). The Janitor can still intercept the packets. However, HTTPS encrypts the application data using TLS. Without the session keys or the ability to trick the users into accepting a fraudulent certificate, the Janitor will only see encrypted ciphertext and cannot read the conversation payload.
\end{itemize}

    \item \textbf{Attacker's Goal:} The primary objective is to execute a \textbf{Man-in-the-Middle (MitM)} attack. By redirecting the victim's traffic through their own machine, the attacker can intercept, read, or modify the data flowing between the victim and the Internet.
    \item \textbf{Steps Required:}
    \begin{enumerate}
        \item The attacker monitors the network to identify a victim (\texttt{192.168.0.3}) sending traffic to the legitimate default gateway (\texttt{192.168.0.1}).
        \item The attacker crafts malicious ICMP Redirect messages (Type 5). These packets must be spoofed to appear as if they originated from the legitimate gateway (\texttt{192.168.0.1}).
        \item The payload of these ICMP Redirect messages instructs the victim to update its routing table, pointing to the attacker's machine (\texttt{192.168.0.4}) as the new, optimal gateway for Internet-bound traffic.
        \item Once the victim updates its routing table, subsequent packets intended for the Internet are sent to the attacker's MAC address instead of the real gateway.
    \end{enumerate}
\end{itemize}

\subsubsection*{Question 2: Identifying Attacker and Victim}
\begin{itemize}
    \item \textbf{Victim IP:} \texttt{192.168.0.3}. This machine is the recipient of the spoofed ICMP Redirect messages and is the one whose HTTP traffic is successfully diverted to the wrong MAC address.
    \item \textbf{Attacker IP:} \texttt{192.168.0.4}. The ICMP Redirect messages explicitly tell the victim to use \texttt{192.168.0.4} as the new gateway. The attacker controls this IP to act as the MitM proxy.
\end{itemize}

\begin{itemize}
    \item \textbf{Is it detectable?} Yes, this specific instance is highly detectable.
    \item \textbf{How to detect:} A normal ICMP Redirect occurs rarely. In the provided logs, we see multiple ICMP Redirect packets (Packets 2, 3, and 4) arriving immediately after a single standard outbound packet. This rapid succession of redirects is anomalous and a strong indicator of spoofing.
    \item \textbf{Mitigation Strategy:}
    \begin{itemize}
        \item \textbf{Host-Level Defense:} Configure the operating system to ignore ICMP Redirect messages entirely.
        \item \textbf{Network-Level Defense:} Implement an IDS/IPS rule: if a host receives multiple conflicting ICMP Redirects in a short timeframe, log an alert and drop the suspicious packets.
    \end{itemize}
\end{itemize}

    \item[\textbf{3.}] Place employee PCs in a separate Office Network segment.
\end{itemize}

    \item \textbf{Attacker's Goal:} To redirect the victim's outbound traffic through the attacker's machine. By intercepting the HTTP request (packet 5), the attacker can eavesdrop on plaintext credentials being sent over the network.

\subsection{Exercise 5 - Network Security}
\subsubsection*{Problem}
Analyze an attack on a Best Salesman Award server using a custom TCP/IP protocol. Explain Blind TCP Hijacking, describe a DoS attack to freeze rankings, and discuss SYN-cookie mitigation.

\subsubsection*{Solution}
Step-by-Step Solution:

\begin{itemize}
    \item[\textbf{1.}] Blind TCP Hijacking Attack:
    \item The custom TCP/IP protocol calculates the Initial Sequence Number (ISN) as the sum of the digits of the current timestamp. This means the ISN is entirely predictable.
    \item Attack Steps: Paolo spoof's his IP address to match his rival, Carminati. He initiates a TCP handshake (SYN) with the server. Since he spoofed his IP, the server's SYN-ACK goes to Carminati (and is ignored or dropped). Paolo doesn't receive the SYN-ACK, making it "blind".
    \item However, because the ISN is predictable based on the timestamp, Paolo calculates the server's ISN and sends the final ACK packet, establishing the connection. He then pushes his payload (the malware) pretending to be Carminati.

    \item[\textbf{2.}] DoS Attack to Freeze Rankings:
    \item If the custom protocol is replaced by standard TCP/IP, Blind Hijacking is much harder because standard ISNs are randomized.
    \item Alternative Attack: Paolo can perform a TCP SYN Flood attack. He sends thousands of SYN requests to the server but never completes the handshake (never sends the final ACK).
    \item Result: The server allocates resources for these "half-open" connections. Eventually, the connection queue fills up, and the server drops legitimate traffic. No one else can upload contracts, freezing the current leaderboard.

    \item[\textbf{3.}] Mitigation:
    \item SYN Cookies: The server can implement SYN Cookies. Instead of allocating memory for a connection upon receiving a SYN, the server cryptographically encodes the connection details into the ISN of its SYN-ACK. It only allocates resources if the client replies with the correct ACK. This completely mitigates the SYN Flood attack without requiring external hardware.
\end{itemize}

\subsection{Exercise 5 - Network Security}
\subsubsection*{Problem}
Analyze a network prank involving DNS Cache Poisoning. Explain how Jim sniffs a DNS request to poison Dwight's DNS cache, and why segmenting the network into different LANs breaks the attack.

\subsubsection*{Solution}
Step-by-Step Solution:

\begin{itemize}
    \item[\textbf{1.}] DNS Cache Poisoning Attack:
    \item Scenario: Jim and Dwight are on the same local network (LAN). Jim wants to redirect Dwight's web traffic from \texttt{beet\_best.com} to \texttt{beet\_scam.com}.
    \item Vulnerability: Standard DNS traffic (UDP port 53) is unencrypted and unauthenticated. To spoof a DNS response, an attacker only needs to match the transaction ID (TxID) and port of the original request.
    \item Steps:
    \item[\textbf{1.}] Jim runs a packet sniffer (like Wireshark) on his machine in promiscuous mode. Since they share a LAN (and assuming a hub or ARP spoofed switch), Jim observes the traffic leaving the local DNS server heading to the Authoritative DNS server.
    \item[\textbf{2.}] Dwight types \texttt{beet\_best.com}. The local DNS server sends a query containing a specific TxID.
    \item[\textbf{3.}] Jim sniffs this query, noting the TxID.
    \item[\textbf{4.}] Jim immediately crafts a forged DNS response packet containing the spoofed IP (81.13.173.234) and the sniffed TxID.
    \item[\textbf{5.}] Jim sends the forged response to the local DNS server. Because Jim is closer on the LAN, his response arrives before the legitimate authoritative server's response. The local DNS server caches the poisoned record and forwards it to Dwight.

    \item[\textbf{2.}] Network Architecture Mitigation:
    \item The network architecture is changed so that employees and the local DNS server are placed on separate LAN segments (separated by a Gateway/Router).
    \item Impact: Packet sniffers only capture broadcast domains (local LANs). Jim is now on a different physical or logical segment than the link between the Local DNS and Authoritative DNS. Jim can no longer sniff the DNS query to read the TxID. Without the TxID, he cannot reliably forge a DNS response that the server will accept, neutralizing the attack.
\end{itemize}
